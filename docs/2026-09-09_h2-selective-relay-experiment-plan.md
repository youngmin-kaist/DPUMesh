# 선택적 디코딩 릴레이 — 연구 검증 실험 플랜 (2026-09-09)

목표는 엔지니어링 최적화가 아니라 **아이디어가 성능 개선을 낸다는 것을 통제된 실험으로 보이는 것**이다.
그래서 플랜의 축은 "무엇을 무엇과 비교해 어떤 수치로 주장하느냐"이고, 구현은 그 비교를 가능하게 하는 최소한으로 잡는다.

## 1. 주장(가설)과 지표
- H1: 정책이 헤더 lookup만 필요할 때, 헤더 블록을 재인코딩 없이 전달하고 정책 필드만 선택 디코딩하면
  h2 종단 프록시 대비 **요청당 CPU(cycles/req)가 줄고 코어당 처리량이 오른다.**
- H2: 이득은 헤더 프로파일(필드 수·크기, 동적 테이블 churn)에 따라 커진다. 즉 "메시 헤더가 무거울수록 유리".
- H3: 정책 판정 결과(allow/deny/route)는 종단 프록시와 동일하다(정확성 손실 없음).
- 지표: (a) cycles/req, (b) 1코어 req/s, (c) p50/p99 지연, (d) 종단→L4 사이 격차 중 회수 비율
  `(T − B1) / (B2 − B1)`, (e) 정책 판정 일치율 100%.

## 2. 비교 대상 — 같은 바이너리, 같은 DMA 데이터패스, 플래그로만 전환
오늘 프로파일이 보여준 함정: linkerd 안에서는 헤더 작업이 요청당 12%(HPACK 5.7% + HeaderMap ~7k cycles)뿐이라
아이디어를 linkerd에 먼저 넣으면 이득이 런타임 오버헤드에 묻혀 **아이디어와 무관하게 "효과 없음"** 으로 보인다.
검증은 헤더 작업 비중이 큰 **얇은 호스트**에서 해야 한다. `dmesh-router-cpp`(1,012줄, nghttp2 종단, 1코어 ~100k req/s)가 그 호스트다.

| 이름 | 모드 | 역할 |
|---|---|---|
| **B1** 종단 | 현재 dmesh-router-cpp: nghttp2 서버+클라이언트 세션, 전체 디코드→HeaderMap→재인코드 | 기준선 |
| **B2** L4 릴레이 | 새로 추가: h2 프레임을 파싱하지 않고 바이트를 그대로 전달(정책 없음) | 상한(speed of light) |
| **T** 선택적 릴레이 | 새로 추가: 연결 1:1 고정 + 미러 HPACK 테이블(`hpack_walk.h`) + 정책 필드만 디코딩 + 블록 그대로 전달 | 아이디어 |
| (참고) linkerd DMA | 17.2–19.8k req/s | 실제 메시 프록시에서의 비중을 보여주는 맥락 |

T는 B1과 B2 사이에 놓인다. **T가 B2에 얼마나 가까운가**가 논문의 그림이다.

## 3. 실험 매트릭스
- 헤더 프로파일 3종 (h2load/wrk2 또는 자체 클라이언트로 요청 헤더 주입):
  P1 gRPC 최소(DSB 실측 블록, 정상 상태 11B), P2 메시 일반(P1 + `uber-trace-id`·baggage·`x-request-id`·`l5d-*` 등 15필드),
  P3 무거움(P2 + `authorization: Bearer <1–2 KB JWT>` + cookie). 각각 동적 테이블 churn 유/무(트레이스 id 고정 vs 매 요청 변경).
- 정책 3종: 없음 / `:path` 프리픽스 라우팅 + `:authority` 확인 / 임의 헤더 N=1,4,8 lookup(allow/deny).
- 부하: 1코어 sharded, h2load `-c1 -m300` ×4 (기존 하네스 `sb-l7.sh`) + gRPC 에코(`dm-bench.sh`). 코어 스윕은 최종 1회.
- 응답 크기 3B(/ok) 고정(헤더 효과만 보기 위해).

## 4. 구현 범위 (비교를 가능하게 하는 최소)
1. `dmesh-router-cpp`에 `DMESH_ROUTER_MODE=terminate|l4|relay` 추가 (`src/router.cpp`, `main.cpp`).
2. `l4`: 채널 페어를 만들고 프레임 경계 무시하고 바이트 복사. (기존 linkerd opaque 경로와 동일 개념, 20줄 수준)
3. `relay`: 프레임 파서(9B) + 스트림별 블록 진행 상태 + 방향별 미러 테이블 2개 + `hw_walk` 확장(정책 헤더 N개, 트레일러 `grpc-status`)
   + 정책 훅(lookup만) + deny 처리(HEADERS 전달, DATA 보류, RST 양방향) + 폴백(미러 불일치 시 그 연결을 terminate로 전환).
   SETTINGS/PING/WINDOW_UPDATE는 그대로 전달, `MAX_FRAME_SIZE`만 min 광고.
4. 검증 도구: 디버그 빌드에서 `relay`가 전체 디코드를 병행해 (i) 미러 테이블 일치, (ii) 정책 판정이 terminate와 동일함을 로그로 확인.
   nghttp2 세션 mem-to-mem 회귀 테스트(`hpack-h2-bench` 스타일).
5. 헤더 추가/수정/삭제는 TODO로 명시(논문에서는 "lookup-only 정책" 가정으로 범위 한정).

## 5. 결과 해석 기준(사전 등록)
- P1(gRPC 최소)에서 T가 B1 대비 cycles/req **≥15% 감소**이면 H1 채택. 미만이면 "헤더 작업이 원래 작다"는 부정 결과로 기록.
- P3에서 감소 폭이 P1보다 크면 H2 채택. 회수 비율 (d)를 프로파일별 그래프로.
- 정책 판정 불일치 0건이어야 H3. 1건이라도 있으면 폴백 조건을 넓히고 재측정.
- 부정 결과도 결과다: 그때는 "종단 비용의 나머지(프레임 처리·복사)가 지배" 라는 프로파일을 같이 낸다.

## 6. 일정
- 1주차: `l4`·`relay` 모드 구현 + 검증 도구 + 마이크로벤치(walk vs term은 이미 있음: 306 vs 1,315 ns).
- 2주차 전반: 1코어 A/B 매트릭스(3 프로파일 × churn × 정책) + 기록. 후반: 코어 스윕 1회, gRPC 에코 1회.
- 선택(3주차): (i) linkerd 통합 — nghttp2 엔진 크레이트 안에 relay 모드, 실제 메시 프록시에서의 이득(≤12% 예상)을 정직하게 보고,
  (ii) DPA 오프로드 — `bench_mode 3`으로 DPA 워커 ns/블록을 먼저 재고, Arm 개입 없는 allow 경로의 가능성만 수치로.

## 7. 오늘 확보한 근거 (재사용)
- 워크 306 ns / 종단 1,315 ns / nghttp2 왕복 3.56 µs (BF-3 Arm, 실제 grpc-go 블록).
- linkerd 1코어 프로파일: 106k cycles/req, 헤더 작업 ≈12%, 전송 3.5%.
- 기존 자산: `DPUMesh/device/hpack_walk.h`(미러 테이블 워커), `hpack_term.h`(폴백), `hpack-h2-bench/`(블록·벤치), `dmesh-router-cpp`(호스트).

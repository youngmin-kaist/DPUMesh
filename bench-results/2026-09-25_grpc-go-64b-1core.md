# gRPC-go 64B echo, DPU ARM 1 core — 2026-09-25

완료: 두 reverse mode × client connection 1–4개 × 3회 = **24회**, 측정 구간 내 **3,296,016 RPC**. 정상 완료된 모든 실행에서 payload mismatch, RPC 오류, 재연결은 0건이었다. 테스트 프로세스는 종료했다.

- `dpu-dma`는 2–4개 연결에서 약 14k RPC/s로 비슷했다.
- `host-dpa`는 1개 연결에서 약 15.2k RPC/s였지만 2–4개 연결에서는 처리량이 감소하고 p99가 약 53–86ms로 증가했다. 긴 tail은 세 반복 모두에서 관측됐으며 원인은 아직 분석하지 않았다.
- 이 결과는 **총 동시 요청 64개에서의 처리량**이다. 동시 요청 수를 sweep하여 최대 처리량을 찾은 결과는 아니다.
- Proxy는 busy polling이므로 CPU 약 100%만으로 처리량 병목 위치를 단정할 수 없다. 측정 구간의 mock control-plane CPU는 0%였다.

## 측정 조건

| 항목 | 설정 |
|---|---|
| 요청 / 응답 | 실제 gRPC-go unary raw-codec echo, application payload 각각 64B |
| Codec | protobuf 직렬화 없이 `[]byte` 사용; HTTP/2·gRPC framing은 별도 |
| DPU CPU | BlueField-3 ARM Cortex-A78AE, CPU 15 한 개 |
| Proxy | 모든 관측 thread의 affinity CPU 15, sharded worker 1, `LINKERD2_PROXY_CORES=1` |
| Accelerator | 기존 per-flow DPA/DMA 사용; ARM core 수에 DPA 연산은 포함하지 않음 |
| DPU dev / rep | `03:00.1` / `0b:00.1` |
| Host | jet1 / `192.168.100.1`, x86 Xeon 6515P, Go 1.27.1 |
| Host CPU | client CPU 0–7, server CPU 8–15, 각각 GOMAXPROCS=8 |
| Host Comch / DPA | `0b:00.1` / `0b:00.0` |
| Workload | 전체 동시 RPC 64: 연결별 64; 32/32; 22/21/21; 16/16/16/16 |
| Backend pool | 각 조건에서 초기 pool과 maximum 모두 client connection 수 P로 설정 |
| 구간 | 연결별 preflight → warmup 3초 → 측정 10초 → drain → native close |
| 반복 | 각 조건 3회, 각 client는 새 process/channel; server는 조건별 재시작 |
| RPC timeout | 각 RPC 5초, client 전체 deadline 90초 |
| Polling | `DMESH_BUSY_POLL=1`, teardown 우회 없음 |
| Logging | Rust WARN; 기존 native ring INFO와 DPU latency 로그는 유지 |
| Control plane | mock identity/destination/policy는 DPU CPU 0–3에 별도 고정 |

1-core 제한은 DPU proxy에 적용된다. x86 client/server는 각각 8개 CPU를 사용할 수 있으며 DPA 하드웨어도 사용한다. 고정 CPU 주파수를 가정하지 않았다. TLS application traffic이나 protobuf 직렬화 비용을 포함한 벤치마크로 해석하면 안 된다.

## 집계와 정확성

- 모든 응답을 worker/sequence별 64B 요청과 비교한다. 연결마다 native dial이 정확히 1회여야 성공이다.
- `[measurement_start, measurement_end)`에 완료된 RPC를 집계한다. Warmup 경계를 걸친 RPC는 완료 시각에 따라 포함하고, 종료 이후 drain은 제외한다.
- 측정된 모든 RPC의 latency를 저장한다. 첫 N개만 사용하는 sampling cap은 없다. Percentile은 nearest-rank 방식이다.
- QPS = 성공 완료 수 / 10초. `QPS × mean latency`가 약 64여서 고정 concurrency와 일치한다.
- CPU는 START/END marker 구간의 `/proc/PID/stat` utime+stime 차이로 계산했다. 100%는 CPU 1개 사용량이다. Proxy 측정 구간은 약 10초이며 tick 경계 때문에 100%를 소폭 넘는 값이 가능하다.
- gRPC가 숨길 수 있는 native `net.Conn.Close` 오류도 수집한다. 정상 결과는 client cleanup까지 성공한 실행만 포함한다.
- 새 도구의 `go test -race ./cmd/channel-bench`와 gofmt 검사 통과. 성능 실행 바이너리는 race instrumentation 없이 빌드했다.

## 중단 실행과 별도 종료 문제

처음 실행은 16개 결과를 저장한 뒤 `host-dpa`, P=2, 두 번째 반복의 warmup 도중 중단됐다. 해당 로그에는 measurement-start marker와 결과가 없어 통계에서 제외했다. 실행 프로세스가 사라진 정확한 원인은 기록만으로 확정하지 못했다.

그 뒤 남아 있던 서버는 SIGTERM으로 20초 안에 종료되지 않았다. SIGQUIT stack에서 `grpc.Server.Stop → http2Server.Close → dmeshgo.Conn.Close → C.dmesh_destroy_qp`에 2분 이상 머문 것이 확인됐다. 이 호출이 transport mutex를 잡아 EQ poller와 다른 Read도 기다렸다. C 내부의 정확한 정체 위치는 Go stack만으로 확정할 수 없다. **비정상 중단 후 native QP 정리 지연은 별도 미해결 문제**이며 이번 성능 측정을 통해 수정했다고 주장하지 않는다.

로그와 stack을 보존하고 해당 proxy/server만 종료한 후, 동일 바이너리·설정으로 새 proxy에서 남은 8회를 재실행했다. 기존 16개 정상 결과는 유지했다. 재개 후 모든 실행과 조건별 server cleanup은 정상 종료했다. 이 때문에 host-dpa P=2의 첫 반복과 나머지 두 반복 사이에는 proxy/server 재시작이 있다.

## 재현

도구: `integrations/grpc/go/cmd/channel-bench`. 상세 환경은 위 표 및 도구 README 참조.

```sh
cd integrations/grpc/go
go test -race ./cmd/channel-bench
go build -a -o bin/channel-bench ./cmd/channel-bench
# 서버는 -mode server. DPUMESH_BACKEND_POOL/MAX=P 설정.
# client connection P=1,2,3,4, 각 3회:
./bin/channel-bench -mode client -connections P -concurrency 64 \
  -warmup 3s -duration 10s -rpc-timeout 5s
```

Proxy는 기존 검증 release 바이너리를 사용했다. 이 측정을 위해 production transport/proxy 코드를 변경하지 않았다. 기존의 다른 API/빌드·concurrency를 사용한 과거 벤치마크와 직접적인 성능 회귀 비교는 하지 않는다.

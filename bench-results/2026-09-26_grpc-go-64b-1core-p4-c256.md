# gRPC-go 64B echo — dpu-dma, 1 ARM core, 4 connections × 64 RPC

Date: 2026-09-26 UTC. Status: **PASS**, three repetitions; 585,367 measured RPC completions. All payloads verified; zero RPC errors or reconnects. Each client had exactly four native connections. Client cleanup passed, server exited 0, and all test proxy/control-plane processes were stopped.

## Results

| Repeat | RPC/s | p50 (ms) | p99 (ms) | Proxy CPU (%) |
|---|---:|---:|---:|---:|
| 1 | 19,498.2 | 13.311 | 17.319 | 99.90 |
| 2 | 19,543.3 | 13.262 | 17.097 | 100.01 |
| 3 | 19,495.2 | 13.316 | 17.029 | 99.89 |
| **Median** | **19,498.2** | **13.311** | **17.097** | **99.90** |

Median columns summarize each run's value; they are not pooled percentiles. Throughput range: 19,495.2–19,543.3 RPC/s. QPS × mean latency is 255.94–256.03, consistent with 256 concurrent RPC loops.

## Comparison

| Measurement | Connections | Concurrent RPC per connection | Total concurrency | RPC/s |
|---|---:|---:|---:|---:|
| Previous current-code benchmark, median of 3 | 4 | 16 | 64 | 14,042.1 |
| This run, median of 3 | 4 | 64 | 256 | 19,498.2 |
| Historical native dpu-dma log, single run | 4 | 64 | 256 | 17,767 |

Increasing only the configured offered concurrency from 64 to 256 with the same binaries increased measured median throughput by **38.86%**. Loaded client p50 increased from 4.588 to 13.311 ms, and p99 from 6.362 to 17.097 ms. This is a throughput/latency comparison at two offered loads, not an unloaded latency measurement.

This result is numerically **9.74%** above the historical native run and around the 18.9–19.1k RPC/s level reported on 2026-09-10. The previous apparent throughput reduction is not reproduced with 64 concurrent RPC per connection. Historical code/build/harness differences remain, so this does not isolate the performance impact of the API changes or prove no regression in other conditions.

## Conditions and verification

- Native `dpu-dma` reverse mode; gRPC-go raw codec unary echo, 64-byte application request and response. No POSIX preload path.
- Exactly four client connections, **64 concurrent RPC loops each (256 total)**; backend pool initial/max both 4.
- Same proxy, host library, DPA kernel artifact and client/server benchmark binaries as the previous current-code benchmark. No source change or rebuild for this run. Final proxy remains ThinLTO/codegen-units=16.
- DPU proxy pinned to CPU 15, one sharded worker, busy polling enabled. All five observed proxy threads had affinity `[15]` at each start/end measurement marker. DPA hardware remains in use.
- x86 client CPU 0–7; server CPU 8–15; GOMAXPROCS=8 each. One ARM core restriction applies to the DPU proxy, not to the x86 endpoints or DPA hardware.
- Per-connection verified preflight, warmup 3 seconds, measure 10 seconds, then drain and native cleanup. RPC deadline 5 seconds. Three sequential client processes; server shared across these three repetitions. Fresh proxy/server for this experiment.
- Every response payload is verified. All completed RPCs in the scheduled measurement interval contribute latency; warmup/drain completions are excluded from reported QPS. Native dials were `[1,1,1,1]` in all runs.
- Mock identity/destination/policy pinned to DPU CPU 0–3; measured aggregate mock CPU was 0% in all repetitions. Proxy CPU near 100% is expected with busy polling and does not identify the bottleneck.
- DPU device/representor `03:00.1` / `0b:00.1`; host Comch/DPA `0b:00.1` / `0b:00.0`. Teardown bypass unset. Logging and all other benchmark configuration match the previous report.
